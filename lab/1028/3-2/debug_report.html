실제 공시를 물었더니 "문서에 없음"이 나온 이유

3-2 멀티 에이전트에 실제 회사(삼성전자) 공시를 물었을 때 공시 담당은 일을 다 했는데 최종 답이 거부로 나왔습니다. 원인을 실행으로 하나씩 좁혀 찾은 과정과 수정 내용을 정리합니다.

증상 
python -m day2.agents "삼성전자(00126380) 최근 1개월 주요 공시를
알려줘 공시 문서 내용도 보여줘"
  • 공시 담당: 목록 1번 + 원문 16번 조회 모두 성공
  • 공시 담당 요약에는 16건 표가 잘 만들어짐
  • 그런데 최종 답: 문서에 없음: 제공된 규정에서 근거를 찾지 못해 답하지 않습니다.
수정 후
  • 같은 질문 4번 중 3번: 공시 16건 내용 + 인용 15~16개로 답
  • 작성자만 반복 실행 14번: 14번 모두 정상
  • A사(녹화 응답) 기본 질문: 정상

남은 1번은 작성자 LLM이 거부를 고른 경우로, 재현되지 않았습니다(⑥ 참고).

  • 같은 조건으로 작성자만 14번 실행 → 14번 모두 정상
  • 작성자 지시문: "규정이 우선", "근거로 답할 수 없으면 sufficient=false"
  • 조사 요약 첫 줄이 규정 담당의 "문서에 없음"

→ 공시만 묻는 질문에서 LLM이 가끔 "규정 근거가 없으니 거부"를 고르는 것으로 봅니다. 지시문 보완으로 줄일 수 있지만 평가 질문의 거부 판단에도 영향을 줄 수 있어 그대로 두었습니다.

이번에 배운 것
  • 작은 녹화 데이터는 버그를 숨깁니다. 실제 데이터를 연결하면 길이, 개수, 형식이 달라집니다.
  • 출력 한도에는 생각 토큰도 들어갑니다. 입력이 길수록 생각이 길어져 답을 쓸 자리가 없어집니다. 종료 사유(stop_reason: max_tokens)를 확인합니다.
  • 조용히 건너뛰는 코드가 원인을 가립니다. except JSONDecodeError: continue 때문에 오류 없이 근거만 사라졌습니다.
  • 가끔 생기는 문제는 여러 번 돌려야 보입니다. 한 번 성공으로 고쳐졌다고 판단하지 않고, 4번·8번씩 돌려 비율로 봤습니다.
  • 중간 상태를 찍어 봅니다. 노드별 입력과 출력(evidence 개수, 답 길이, 종료 사유)을 기록하면 어디서 끊겼는지 바로 보입니다.

분석에 쓴 방법

방법무엇을 봤나
전체 그래프 실행 + state 출력작업 분배, 도구 호출, 요약, evidence 개수, 검증 결과, 최종 답
LLM 없이 데이터만 측정도구 결과 JSON 길이, 1,500자로 자르면 읽히는지
노드 하나만 실행공시 담당(disclosure)만 따로 돌려 evidence가 만들어지는지
감시 코드(spy) 끼우기공시 담당의 반복 횟수, 마지막 응답의 블록 종류, 종료 사유, 생각 토큰 수
입력 고정 후 반복작성자 입력을 저장해 작성자만 6번·8번 실행, 거부 비율과 출력 토큰
