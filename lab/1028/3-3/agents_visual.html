왜 빨라지나

        
    
          
  • 두 담당은 서로의 결과가 필요 없습니다. 그래서 동시에 시작해도 됩니다.
    • 
          
  • 규정 담당은 별도 스레드(asyncio.to_thread)에서, 공시 담당은 비동기(MCP 도구)로 돌아 실제로 겹칩니다.
    • 
          
  • 모으기(collect)는 둘 다 끝날 때까지 기다린 뒤 작성자로 넘어갑니다.
    • 
        

      
바뀌지 않는 것

        
    
          
  • 토큰과 비용: 같은 일을 하므로 거의 같습니다(질문당 48,148 → 50,662).
    • 
          
  • 답을 쓰는 곳: 여전히 작성자 하나입니다. 읽기는 병렬, 쓰기는 하나.
    • 
          
  • 호출 한도: 동시에 부르는 LLM 수가 늘어 429 오류가 나기 쉬워집니다. 그럴 때는 PARALLEL = False로 바꿉니다.
    • 
        

    

  


  
  

    
두 담당이 같은 state의 evidence에 동시에 씁니다. 누적 항목(operator.add)이라 서로 덮어쓰지 않고 이어 붙습니다. 작성자는 dedupe()로 같은 근거를 한 번만 남긴 뒤 답을 씁니다. 

    

      
규정 담당

      
공유 state · evidence 

      
공시 담당

    

    

      
같은 근거를 판단하는 기준

      
네 칸이 모두 같으면 같은 근거입니다: source_typedoc_or_rceptarticle_or_dateas_of

      
중복은 주로 검증 실패로 담당을 다시 부를 때 생깁니다. 다시 조사한 근거가 앞의 근거 뒤에 또 붙기 때문입니다. 3-2(중복 제거 없음)에서 되돌림이 일어난 실행에서는 근거가 16건에서 32건으로 두 배가 된 적이 있습니다.

    

  


  
  

    

      

        
정답 코드에서 3-2 → 3-3 바뀐 곳

        

          
-PARALLEL = False   # 3-2: 담당 에이전트를 차례로 실행

          
+PARALLEL = True    # 3-3: 병렬 조사(Send). 오류가 나면 False로

          
-DEDUPE = False     # 3-2: 근거 중복 제거 없음

          
+DEDUPE = True      # 3-3: 같은 근거는 중복 제거

        

        
정답 코드는 3-2부터 evidence state와 작성자 하나 구조를 넣어 두었습니다. 그래서 3-3에서는 이 두 값만 바뀝니다. 수강생이 3-2를 감독자 구조만으로 만들었다면, 3-3 지시문으로 evidence와 writer를 새로 넣게 됩니다.

      

      

        
두 값이 바꾸는 동작

        

          
False (3-2)True (3-3)

          
PARALLEL감독자가 첫 담당에게만 Send. 담당이 끝나면 다음 담당에게 Send감독자가 모든 담당에게 Send를 한꺼번에. 모두 끝나면 모으기로

          
DEDUPEevidence를 그대로 작성자에게네 칸이 같은 근거는 하나만 남김

        

      

    

    
코드에서 갈리는 곳

    

      
dispatch() · 감독자 다음

sends = [Send(name, {"question": q, "role": ..., "feedback": ...})
         for name, q in state["tasks"].items()]
return sends if PARALLEL else sends[:1]

      
writer() · 작성자 시작

ev = dedupe(state["evidence"]) if DEDUPE else state["evidence"]
# key = (source_type, doc_or_rcept, article_or_date, as_of)
